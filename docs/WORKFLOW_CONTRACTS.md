# Workflow and access contracts

## Account and personal data

Administrators open a user's access editor for lifecycle actions. Deactivation is checked on every new REST/MCP/replay request; existing SSE streams recheck local deactivation/logout every ten seconds. Self-deactivation and removal of the last active administrator are rejected. Reactivation is explicit. IdP membership removal still follows provider token/introspection timing: the application does not synchronize the provider directory automatically.

`GET /api/users/{id}/lifecycle` reports custody, keeper assignments and up to 200 owned resources/groups. Bulk transfer accepts at most 200 selected ownership IDs and an active successor; it reports each blocked resource. Reload after a batch to see the remaining ownership. Private ownership transfers require settled custody, reservations and transfers; account-owned items have no commitment checks. Custody requires real return/handover processing; keeper assignments use the existing location responsibility workflow. Group ownership can be transferred without changing membership. Deactivation retains historical grants; inactive people cannot receive new assignments or shares.

`GET /api/users/{id}/personal-data/export` is admin-only and returns a ZIP of person-linked relational records, indirect event attendances and a media manifest. It rejects exports over 25,000 rows, a two-MiB row or a 25-MiB compressed bundle. Authenticated media endpoints supply the files separately. Unlinked names/free text need a manual search and evidence review.

Pseudonymization requires a reason, revision and resolved custody, keeper assignments and ownership. It replaces account and linked attendee display data, clears memberships, direct shares, notices and reminders, and disables the account. It retains the actor UUID and issuer/subject to preserve history and prevent automatic re-provisioning. It is pseudonymization, not irreversible anonymous erasure. Historical free text, uploaded acknowledgements, outbox/log exports, IdP records and backups require the operator's documented retention/redaction procedure. The workflow does not silently rewrite stock history.

Transient retention runs daily in batches of at most 1,000: terminal notifications after 180 days, inactive reminders after 180 days, and unlinked attendees whose events all ended over 730 days ago are pseudonymized. Configure `inventory.retention.notifications-days`, `reminders-days`, and `unlinked-attendees-days`; zero disables that category. Business movement/history records have indefinite retention until an explicit operator policy changes it. Abandoned staged media has its existing purge job.

## Private items and sharing

Account-owned items choose public/private availability on creation and owner/admin edits. Public availability enables faction and general orders without commitments; ordinary stock, damage and maintenance checks remain. The creator becomes responsible automatically. Editors may assign an account or a free-text contact; without warehouse access, accounts are limited to self and sharing-group peers. Assignment does not grant access; free text sends no notifications. Sharing changes require no reason and retain revision checks/auditing. Below Overview, one named list combines owner, admins, individual people and groups, merging duplicate permissions; private location details remain protected. Sharing-group members can see their peers by name directly on Sharing and Users.

## Inventory allocation and private operations

General orders may omit an event throughout submission, pickup, return and restock. Preparation accepts `sourceAllocations` as item UUID -> position UUID -> positive integer quantity. Quantities must sum to the prepared quantity; positions must belong to the item and be usable/authorized. Omission allocates across accessible internal positions in FEFO order, using the earlier non-null expiry/best-before date. Serialized preparation continues to select exact assets. Reservations reference positions and pickup emits the corresponding source/lot movements.

Bulk/lot returns and unused restocks settle original checkout-position allocations in `issueQuantities`. Partial settlements cannot exceed the issued quantities, selected lots must match the issue, and reversals negate those settlements. Order returns use the configured return location, otherwise home. Pending return instructions block home/return-place changes until review. Automatic multi-lot reconciliation records provenance; it does not attest physical batch labels.

Assembly checkout reviews exact serialized units and bulk/lot source quantities before one atomic transaction batch. Each row retains its command key for identical retries; changed payloads receive new keys. Assemblies remain recipes rather than physical kit stock.

Private owners/editors may issue stock, transfer between editable places, run scoped counts, and review direct private returns. Public-use visibility does not grant return-review administration. Organization operations and order return review retain their role requirements. Item access and every source/destination are independently authorized; tenant lists remain private-scoped.

Operational quantities are integer whole units or percentage steps with capacity context; 100 percentage steps represents one full unit. Purchasing prices are per full unit. CSV identifies items by ItemId/SKU or an unambiguous name (optionally matched by home), preserves omitted measure metadata, and rejects fractional steps. Role, tracking mode and measure settings are immutable after stock history/assets exist.

Bulk damage records the exact position when more than one is possible. Repair/write-off resolves those quantities. Unlocated bulk stock can be put away by assigning a home, including its unresolved damage allocations, without adding owned stock. New lot stock requires both lot and receiving location. Inbound stock and serialized registration/relocation require active destinations and ancestors.

## Reminders and external delivery

The action inbox derives live tasks. Authorization uses typed source IDs before task titles/details are returned. A selected reminder creates a generic persisted notice when due. The hourly digest checks currently visible pickup, overdue-order, expiry and maintenance work, at most 500 recipients per run, once per business day. Notices may outlive completed tasks; opening the app always shows current authorized work.

Set `inventory.notifications.webhook-url` to an HTTPS gateway and optionally `inventory.notifications.webhook-token`. `inventory.public-url` is the sign-in link. Delivery is disabled until a URL is configured. The gateway receives notification UUID, recipient email and generic sign-in text; no task/resource text or identifiers leave the app. It must deduplicate `Idempotency-Key`. Delivery is at least once, with a two-minute lease, eight attempts and capped exponential retry. Statuses are `pending`, `sending`, `retry`, `sent`, `skipped`, `failed`; inactive/ineligible recipients are skipped. A successful HTTP response means gateway acknowledgement, not proof of final email/push receipt. Configure and verify the gateway separately; no external messages are sent during local tests.

ntfy push runs alongside the webhook. `inventory.notifications.ntfy-url` enables it: HTTPS, or plain HTTP to an ntfy container on the internal network; `ntfy-public-url` (default: `ntfy-url`) is the subscribe address shown to users; authenticate with `ntfy-token` (Bearer) or `ntfy-username`/`ntfy-password` (Basic). Each user sets a personal topic on the profile page (`GET`/`PUT /api/notifications/settings`, stored in `app_users.ntfy_topic`, cleared on pseudonymization) and receives the same generic text as the webhook. `POST /api/notifications/settings/ntfy-test` publishes a fixed test message to the saved topic (400 without server or topic, 502 when the server does not acknowledge).

Users can also set a personal webhook URL there (`app_users.webhook_url`, returned only to its owner, cleared on pseudonymization). It must be HTTPS without embedded credentials, and its host must resolve only to public addresses (no loopback, private, link-local, CGNAT, unique-local or multicast); this is checked on save and again before each post, and redirects are never followed. The webhook receives JSON `id`, `subject`, `text`, `content` (text plus sign-in link, for Discord-style receivers) and `url`, with `Idempotency-Key: <id>`. Personal webhooks need no deployment configuration, so notification workers always claim notices.

Each channel's acknowledgement is stored in `notifications.delivered_channels` (`gateway`, `webhook`, `ntfy`); retries post only to channels that have not acknowledged. A notice is `sent` once every applicable channel acknowledged; with none it is `skipped`. ntfy has no idempotency key, so a lost acknowledgement can repeat a message.

Admin topics (`ntfy-topics.items`, `.assemblies`, `.users`; `none` disables one) come from the durable integration consumer `ntfy-topics`: item/assembly `catalog.changed` events (filtered by `items-actions`/`assemblies-actions`: `created`, `updated`, `deleted`; default `created,deleted`) and `user.created`, `user.changed`, `user.pseudonymized`. Each `ntfy-topics.interval` (default 60s) posts one summary per topic and action (up to 10 names, then a count) with names and actor, linking to the record or list. Private resources are never posted. Unacknowledged events return after the two-minute lease and are dropped after five attempts. The subscription is removed while ntfy or every topic is disabled, so it never blocks the outbox purge. On public ntfy servers topics are readable by anyone: use unguessable names or ntfy access control. Users cannot save an admin topic (case-insensitive) as their personal topic, so the API never posts personal or test notices into it.

## Custody and corrections

Generated handovers record what the application posted; they no longer automatically attest physical condition. Warehouse staff record explicit condition confirmation/notes and optional uploaded acknowledgement evidence. Evidence is append-only, bound to its handover and readable only with access to its order. Attachments use authenticated media access. Capture and upload require connectivity. Both order kinds show the evidence panel.

Administrators can reverse the latest direct addition, adjustment, checkout or check-in through a linked compensating movement, with a reason and command ID. Original facts remain unchanged. Reversal rows record the executing administrator in `reversedBy`; `userId` stays the original custody beneficiary. Reservations, pending returns, subsequent movements and changed assets can block reversal. Document-driven purchases, counts, transfers, orders and damage use their own reconciliation workflows. Quantities on reversal rows are signed; usage counters subtract reversed checkouts. Database triggers reject changes/deletion of committed movement, order, handover, reconciliation, runtime, maintenance and sync history. Initial finalization in the inserting transaction remains allowed.

## Damage reports and quantity resolution

The Damage reports page reads `GET /api/damage-reports` with zero-based `page`, `size`, optional `search`, optional `itemId`/`assetInstanceId`/`assemblyId`, and repeated `status` parameters. The response is a row array with `X-Has-More` continuation. Search matches description, item/assembly name and asset code in the database before pagination. The page uses 20, 50 or 100 rows and resets to page zero when its tab or search changes.

| Tab | Requested statuses |
|---|---|
| Open | `reported`, `triaged`, `awaiting_repair`, `in_review`, `in_repair` |
| History | `repaired`, `verified`, `returned_to_service`, `written_off`, `resolved` |

The tabs are disjoint; History is never an unfiltered collection read. The desktop and mobile lists omit descriptions, resolution comments and activity. History also omits severity and editing. An info modal shows the description, accumulated resolution notes, reporter and current handling details. The REST projection supplies current status and reporter/handler summaries, rather than a complete per-transition timeline.

**Start repair** opens a modal without posting a status change. The page requires a repair/write-off choice, a positive integer quantity up to the unresolved amount, and a nonblank action comment. Submission uses `PATCH /api/damage-reports/{id}`:

```json
{ "status": "repaired", "amount": 2, "notes": "Replaced connectors and checked operation" }
```

The resolution input contains `status`, `amount`, `notes`, `idempotencyKey`, `description`, `severity` and `occurredAt`; `itemHint` is no longer part of the contract. Description/severity edits use the same endpoint without a status. The service also accepts `in_review` for triage. The backend checks warehouse permission, requires admin permission for write-off, locks the report, rejects quantities above the unresolved amount, and appends trimmed nonblank notes to `resolutionNotes`. The comment requirement is enforced by the page; internal repair-case commands retain their existing notes contract.

`unresolved = amount - repairedAmount - writtenOffAmount`. After quantity resolution, remaining units keep the report `in_review`; with none remaining, all repaired units produce `repaired`, all written-off units produce `written_off`, and mixed outcomes produce `resolved`. Existing change events refresh the page and related stock readers. Failed saves retain modal input; resolving the last row on a later page returns to the previous page. Repairs restore condition without creating owned stock; write-off reduces stock. The Operations repair-case verification/release lifecycle remains separate.

## Events, reports and readers

An optional event order deadline blocks creation, edits and submission after the instant; preparation, returns and cancellations retain their normal lifecycle rules. The event edit dialog uses local date/time input. Copying an earlier order creates an independent draft for an open event with current permissions/catalog validation. It preserves faction-order assembly grouping and resolves components from the current assembly recipe; general orders copy item quantities. The new draft carries no preparation, reservations, custody or evidence.

Reports rebuild on open when absent, over five minutes old or source revisions differ. A transaction fence allows one rebuild per report. Contended on-open reads return the last committed snapshot marked stale (or an empty stale view before the first generation); an explicit rebuild command still returns a retryable 409. PostgreSQL applies privacy, filters, counts, monthly totals and pagination inside snapshot JSON; the application decodes only the page. Rebuilding still materializes source data and the full snapshot. Export pins one generation, rejects replaced generations and caps output at 25,000 rows. See [performance acceptance](PERFORMANCE_ACCEPTANCE.md).

Main operational lists scope private relationships in PostgreSQL before paging. Targeted response/media redaction remains a second boundary. Shared people-directory entries expose only active IDs and display names to authenticated accounts, including tenants so they can share resources. Nested actor summaries contain ID/display name/username; full email, role and faction data remain in authorized self/admin responses. Visible child locations omit hidden ancestor names/codes; depth is null whenever any ancestor is hidden. Such visible children remain stock-holding places. Location edits use explicit `keepParent` when the parent is undisclosed. Location search uses its own code/name, preventing hidden ancestor-code inference.

Maintenance schedules are the only stored calendar/meter policy. Item/asset due dates and status are derived projections. Item-wide schedules apply to every asset; asset schedules apply to that asset. Parent-item summaries aggregate active schedules for active assets; attention filters use each schedule warning window and live signed counters. Category defaults create ordinary date schedules (per asset for serialized equipment); clearing a category default retires only its generated schedules. Safety flags remain separate. Inspections advance the selected schedule, never an unrelated sibling's schedule.
