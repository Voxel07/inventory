# Workflow and access contracts

## Account and personal data

Administrators open a user's access editor for lifecycle actions. Deactivation is checked on every new REST/MCP/replay request; existing SSE streams recheck local deactivation/logout every ten seconds. Self-deactivation and removal of the last active administrator are rejected. Reactivation is explicit. IdP membership removal still follows provider token/introspection timing: the application does not synchronize the provider directory automatically.

`GET /api/users/{id}/lifecycle` reports custody, keeper assignments and up to 200 owned resources/groups. Bulk transfer accepts at most 200 selected ownership IDs and an active successor; it reports each blocked resource. Reload after a batch to see the remaining ownership. Existing idle/commitment checks apply. Custody requires real return/handover processing; keeper assignments use the existing location responsibility workflow. Group ownership can be transferred without changing membership. Deactivation retains historical grants; inactive people cannot receive new assignments or shares.

`GET /api/users/{id}/personal-data/export` is admin-only and returns a ZIP of person-linked relational records, indirect event attendances and a media manifest. It rejects exports over 25,000 rows, a two-MiB row or a 25-MiB compressed bundle. Authenticated media endpoints supply the files separately. Unlinked names/free text need a manual search and evidence review.

Pseudonymization requires a reason, revision and resolved custody, keeper assignments and ownership. It replaces account and linked attendee display data, clears memberships, direct shares, notices and reminders, and disables the account. It retains the actor UUID and issuer/subject to preserve history and prevent automatic re-provisioning. It is pseudonymization, not irreversible anonymous erasure. Historical free text, uploaded acknowledgements, outbox/log exports, IdP records and backups require the operator's documented retention/redaction procedure. The workflow does not silently rewrite stock history.

Transient retention runs daily in batches of at most 1,000: terminal notifications after 180 days, inactive reminders after 180 days, and unlinked attendees whose events all ended over 730 days ago are pseudonymized. Configure `inventory.retention.notifications-days`, `reminders-days`, and `unlinked-attendees-days`; zero disables that category. Business movement/history records have indefinite retention until an explicit operator policy changes it. Abandoned staged media has its existing purge job.

## Reminders and external delivery

The action inbox derives live tasks. Authorization uses typed source IDs before task titles/details are returned. A selected reminder creates a generic persisted notice when due. The hourly digest checks currently visible pickup, overdue-order, expiry and maintenance work, at most 500 recipients per run, once per business day. Notices may outlive completed tasks; opening the app always shows current authorized work.

Set `inventory.notifications.webhook-url` to an HTTPS gateway and optionally `inventory.notifications.webhook-token`. `inventory.public-url` is the sign-in link. Delivery is disabled until a URL is configured. The gateway receives notification UUID, recipient email and generic sign-in text; no task/resource text or identifiers leave the app. It must deduplicate `Idempotency-Key`. Delivery is at least once, with a two-minute lease, eight attempts and capped exponential retry. Statuses are `pending`, `sending`, `retry`, `sent`, `skipped`, `failed`; inactive/ineligible recipients are skipped. A successful HTTP response means gateway acknowledgement, not proof of final email/push receipt. Configure and verify the gateway separately; no external messages are sent during local tests.

## Custody and corrections

Generated handovers record what the application posted; they no longer automatically attest physical condition. Warehouse staff record explicit condition confirmation/notes and optional uploaded acknowledgement evidence. Evidence is append-only, bound to its handover and readable only with access to its order. Attachments use authenticated media access. Capture and upload require connectivity. Both order kinds show the evidence panel.

Administrators can reverse the latest direct addition, adjustment, checkout or check-in through a linked compensating movement, with a reason and command ID. Original facts remain unchanged. Reversal rows record the executing administrator in `reversedBy`; `userId` stays the original custody beneficiary. Reservations, pending returns, subsequent movements and changed assets can block reversal. Document-driven purchases, counts, transfers, orders and damage use their own reconciliation workflows. Quantities on reversal rows are signed; usage counters subtract reversed checkouts. Database triggers reject changes/deletion of committed movement, order, handover, reconciliation, runtime, maintenance and sync history. Initial finalization in the inserting transaction remains allowed.

## Events, reports and readers

An optional event order deadline blocks creation, edits and submission after the instant; preparation, returns and cancellations retain their normal lifecycle rules. The event edit dialog uses local date/time input. Copying an earlier order creates an independent draft for an open event with current permissions/catalog validation. It preserves faction-order assembly grouping and resolves components from the current assembly recipe; general orders copy item quantities. The new draft carries no preparation, reservations, custody or evidence.

Reports rebuild on open when absent, over five minutes old or source revisions differ. A transaction fence allows one rebuild per report. Contended on-open reads return the last committed snapshot marked stale (or an empty stale view before the first generation); an explicit rebuild command still returns a retryable 409. PostgreSQL applies privacy, filters, counts, monthly totals and pagination inside snapshot JSON; the application decodes only the page. Rebuilding still materializes source data and the full snapshot. Export pins one generation, rejects replaced generations and caps output at 25,000 rows. See [performance acceptance](PERFORMANCE_ACCEPTANCE.md).

Main operational lists scope private relationships in PostgreSQL before paging. Targeted response/media redaction remains a second boundary. Shared people-directory entries expose only active IDs and display names to authenticated accounts, including tenants so they can share resources. Nested actor summaries contain ID/display name/username; full email, role and faction data remain in authorized self/admin responses. Visible child locations omit hidden ancestor names/codes; depth is null whenever any ancestor is hidden. Such visible children remain stock-holding places. Location edits use explicit `keepParent` when the parent is undisclosed. Location search uses its own code/name, preventing hidden ancestor-code inference.

Maintenance schedules are the only stored calendar/meter policy. Item/asset due dates and status are derived projections. Item-wide schedules apply to every asset; asset schedules apply to that asset. Parent-item summaries aggregate active schedules for active assets; attention filters use each schedule warning window and live signed counters. Category defaults create ordinary date schedules (per asset for serialized equipment); clearing a category default retires only its generated schedules. Safety flags remain separate. Inspections advance the selected schedule, never an unrelated sibling's schedule.
