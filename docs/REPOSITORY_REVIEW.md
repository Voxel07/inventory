## 3. Prioritized findings

Severity: **P1/high** requires correction before acceptance; **P2/medium** is a concrete correctness/performance/refactoring concern; **P3/low** is cleanup. Confidence describes source evidence, not a successful runtime reproduction. Effort is relative: S = localized, M = several collaborators, L = cross-cutting. Verification below is proposed and remains pending unless listed in section 1.

### A01 — Assembly reads expose components outside item visibility

**P1/high · high confidence · CAT-05, SEC-01, API-01, F09.**

Evidence: [backend/src/main/java/org/ash/inventory/resource/CatalogResource.java:117](../backend/src/main/java/org/ash/inventory/resource/CatalogResource.java#L117) authenticates but returns one shared assembly cache. [backend/src/main/java/org/ash/inventory/resource/CatalogResponseCache.java:64](../backend/src/main/java/org/ash/inventory/resource/CatalogResponseCache.java#L64) has no actor argument. [backend/src/main/java/org/ash/inventory/resource/ApiMapper.java:263](../backend/src/main/java/org/ash/inventory/resource/ApiMapper.java#L263) maps every component into an ItemResponse; [backend/src/main/java/org/ash/inventory/service/ApiQueryService.java:101](../backend/src/main/java/org/ash/inventory/service/ApiQueryService.java#L101) also loads the assembly without per-component visibility. Compare [backend/src/main/java/org/ash/inventory/helper/security/ActorService.java:102](../backend/src/main/java/org/ash/inventory/helper/security/ActorService.java#L102) and the scoped item query in CatalogOrm.

Trigger: staff adds a person/group item to an assembly; an unrelated authenticated account lists or opens that assembly. The expansion includes the otherwise-hidden item, descriptive fields, media and assigned-user/location data. Client filtering cannot repair an API disclosure.

Change: own visible assembly projection in the catalog query boundary. Define whether an assembly with hidden components is hidden in full or returned with explicitly limited data; never treat partial component data as an executable complete assembly. Apply that policy to list, detail and nested expansions. Cache only a genuinely public projection or an actor/policy-scoped response.

**Effort M; regression risk high** (assembly selection and quantities). Verify with two distinct person/group accounts, staff and read-only, on warm and cold cache, list/detail/order expansion and create-from-assembly commands.

### A02 — Account isolation is incomplete across QueryClient, token refresh and response completion

**P1/high · high confidence · OFF-02, SEC-01, F16, C05.**

Evidence: [src/App.tsx:53](../src/App.tsx#L53) survives logout; [src/hooks/useItems.ts:17](../src/hooks/useItems.ts#L17) and [src/hooks/useOrders.ts:13](../src/hooks/useOrders.ts#L13) use account-independent keys. `useAuth` and `AppContent` contain no query cancellation/clearing on identity change. In [src/services/authManager.ts:160](../src/services/authManager.ts#L160), a global refreshPromise applies its result via `replaceTokens` without checking the originating session; `clearAuth` does not invalidate it. [src/services/apiClient.ts:180](../src/services/apiClient.ts#L180) checks identity after headers but before the later `response.json()` await. [src/services/resourceFactory.ts:50](../src/services/resourceFactory.ts#L50) then scopes the saved body to the account current at that later call.

Triggers: A logs out and B signs in while caches are fresh; A's refresh resolves after logout/B sign-in; or the account changes while A's body parses. B can see cached A data, receive A's tokens, or acquire A data in B's IndexedDB catalog namespace. Existing queue owner checks and actor-qualified ETag keys help but do not close these races.

Change: introduce an identity/session generation. Cancel active reads, clear or replace the QueryClient and UI drafts on identity change, scope every personalized query, reject refresh results from an obsolete generation, and pass the captured account through the entire request/cache write. Recheck after each awaited body operation; a write rejected locally after account change may already have committed and must retain command evidence.

**Effort L; regression risk high** (offline cold start and refresh). Verify A→B→A transitions with fresh/stale queries, delayed refresh/body/IndexedDB access, pending writes, logout and role changes. Preserve each account's durable queue/history.

### A03 — Serialized count posting accepts a stale physical snapshot

**P1/high · high confidence · INV-02/04, F10, C09.**

Evidence: [backend/src/main/java/org/ash/inventory/orm/CountOrm.java:52](../backend/src/main/java/org/ash/inventory/orm/CountOrm.java#L52) snapshots active assets at locations. [backend/src/main/java/org/ash/inventory/service/CountService.java:167](../backend/src/main/java/org/ash/inventory/service/CountService.java#L167) later locks each asset but, for an approved zero count, assigns `lost` without validating snapshot location, active/state/version, reservations or custody. The neighboring bulk branch checks the expected on-hand quantity; serialized posting has no equivalent condition. The asset's optimistic version detects simultaneous stale writes, not a sequentially stale count applied to the latest loaded entity.

Trigger: snapshot → asset reserved, checked out or transferred → old zero observation approved and posted. The command replaces current asset state while retaining contradictory order/reservation/custody evidence. This requires no simultaneous transaction to fail.

Change: retain and validate asset snapshot evidence under the normal item→asset lock policy; reject changed identity/location/state/revision and require recount or explicit reconciliation. Audit bulk posting's interaction with held/reserved quantities and lock order separately; do not assume its quantity comparison establishes all invariants.

**Effort M; regression risk high.** Verify sequential and concurrent reserve/checkout/transfer/return/retirement between snapshot and post, plus no-change zero/one observations and independent approval. A conflict must post no adjustment or partial state change.

### A04 — Rejecting a stale return resurrects the submission's former asset state

**P1/high · high confidence · RET-02, INV-04, F08/F20.**

Evidence: [backend/src/main/java/org/ash/inventory/service/ReturnSubmissionService.java:144](../backend/src/main/java/org/ash/inventory/service/ReturnSubmissionService.java#L144) unconditionally restores `previousAssetState` for direct/faction serialized submissions. `pending(id)` locks the submission, not the item/asset, and only checks submission status. [backend/src/main/java/org/ash/inventory/service/InventoryOperationsService.java:179](../backend/src/main/java/org/ash/inventory/service/InventoryOperationsService.java#L179) demonstrates an independent check-in can already update physical asset state.

Trigger: a return waits for acknowledgement; stock is reconciled through another authorized path; staff reject the obsolete submission. The rejection restores `in_field`/`in_custody` even though the asset was returned, re-reserved, repaired or otherwise changed. Original documentation explicitly permits rejecting stale submissions with an explanation.

Change: lock using the established aggregate order, always preserve rejection evidence, and undo the pending-check marker only if the current state still belongs to this submission and custody remains unresolved. Never overwrite later domain state using a historical snapshot.

**Effort M; regression risk high.** Verify direct/faction pending returns, normal rejection, independent return/write-off/re-reservation before rejection and concurrent decisions. General-order submission handling remains domain-specific.

### A05 — Planning snapshot and action inbox bypass the shared maintenance evaluator

**P2/medium · high confidence · MNT-01, PRC-01, F02/F13/F21, C04 regression.**

Evidence: [backend/src/main/java/org/ash/inventory/service/MaintenancePolicy.java:14](../backend/src/main/java/org/ash/inventory/service/MaintenancePolicy.java#L14) classifies missing due/meter evidence as unknown and blocks unknown/due. [backend/src/main/java/org/ash/inventory/service/InventoryOperationsService.java:602](../backend/src/main/java/org/ash/inventory/service/InventoryOperationsService.java#L602) evaluates item-wide schedules using item counters before evaluating an exact asset. [backend/src/main/java/org/ash/inventory/service/PlanningStockService.java:163](../backend/src/main/java/org/ash/inventory/service/PlanningStockService.java#L163) instead evaluates every applicable meter schedule using the individual asset's hours/count, including item-wide schedules. [backend/src/main/java/org/ash/inventory/service/ActionInboxService.java:57](../backend/src/main/java/org/ash/inventory/service/ActionInboxService.java#L57) implements another warning/due evaluator. The snapshot also treats null dueAt/dueValue as not due, but [LifecycleService.java:83](../backend/src/main/java/org/ash/inventory/service/LifecycleService.java#L83) rejects missing required thresholds on ordinary schedule creation/update; that null divergence is a defensive-policy gap, not a demonstrated normal API trigger. Item/asset hour columns are non-null in the baseline.

Trigger: a committed serialized pool has an item-wide usage/hour schedule whose item counter is due while each offered asset's counter is below the threshold. Planning can credit assets that checkout rejects. Missing-threshold handling differs only if invalid persisted evidence reaches these readers; no such state was created or observed in this review. Inbox independently implements the policy and would omit unknown schedule evidence. Actual checkout still uses the authoritative guard; this is inconsistent planning/reminder behavior, not evidence that checkout is bypassed.

Change: supply a typed snapshot of schedule facts and correct item/asset counters to one pure maintenance evaluator. Reuse it for planning, reports, inbox, reservation and checkout; keep request-local data and avoid reintroducing database queries in planning loops.

**Effort M; regression risk high.** Verify null thresholds/meters, warning/due boundaries, item-wide versus asset-specific date/hour/count schedules and live-versus-snapshot parity.

### A06 — Serialized item totals count in-transit assets as on hand

**P2/medium · high confidence · INV-01, PRC-01, F05/F06/F17.**

Evidence: [backend/src/main/java/org/ash/inventory/service/TransferService.java:116](../backend/src/main/java/org/ash/inventory/service/TransferService.java#L116) clears physical location at dispatch. [backend/src/main/java/org/ash/inventory/service/InventoryOperationsService.java:282](../backend/src/main/java/org/ash/inventory/service/InventoryOperationsService.java#L282) increments onHand for every non-custody, non-lost/written-off asset, including in_transit. [backend/src/main/java/org/ash/inventory/service/OperationalReportService.java:147](../backend/src/main/java/org/ash/inventory/service/OperationalReportService.java#L147) explicitly excludes transit from onHand in the report, exposing a competing definition.

Trigger: serialized transfer dispatched but not received. Item/procurement stock says it is on hand while the location/report view says transit. Availability is already zero for this state; the misleading physical/owned totals remain the defect. Simply subtracting transit from onHand would also lower `totalOwned()` unless transit ownership is represented separately.

Change: define and share a stock classification including transit ownership, warehouse onHand, custody and availability. Preserve owned material in transit; update DTO/client totals together and keep exact asset identity.

**Effort M; regression risk high** (stock and valuation semantics). Verify dispatch/partial receipt/discrepancy/completion, bulk/serialized parity and loan provider transfers; compare item, planning, position and report views.

### P01 — Batched image loading falls back to one query per imageless item

**P2/medium · high confidence · API-01, C01; catalog performance.**

Evidence: [backend/src/main/java/org/ash/inventory/orm/CatalogOrm.java:120](../backend/src/main/java/org/ash/inventory/orm/CatalogOrm.java#L120) groups only returned image rows. [backend/src/main/java/org/ash/inventory/resource/ApiMapper.java:138](../backend/src/main/java/org/ash/inventory/resource/ApiMapper.java#L138) passes `imagesMap.get(id)`; [backend/src/main/java/org/ash/inventory/resource/ApiMapper.java:151](../backend/src/main/java/org/ash/inventory/resource/ApiMapper.java#L151) interprets missing-map/null as “not loaded” and queries the item again. The batch assembly mapper has the same pattern.

Trigger: catalog page/component expansion with items having no images. Each such item incurs a redundant explicit image lookup after the batch query. This is a confirmed query multiplier; measured latency and Hibernate first-level effects are not claimed.

Change: distinguish “batch loaded, empty” from “not provided,” passing `getOrDefault(id, List.of())` or a fully populated projection. Keep individual detail loading explicit.

**Effort S; regression risk low.** Verify mixed/all-empty/all-populated image sets and repeated components with SQL counts; image lookup count should remain bounded by batch operations, not imageless-item count.

### P02 — Catalog/operational response mapping still chooses per-row database work

**P2/medium · high confidence · API-01, INV-01, F01/F05, C01 incomplete.**

Evidence: [backend/src/main/java/org/ash/inventory/service/InventoryOperationsService.java:244](../backend/src/main/java/org/ash/inventory/service/InventoryOperationsService.java#L244) batches ledger/damage/reservations/assets, then invokes per-item stock and `withPolicy`. [backend/src/main/java/org/ash/inventory/service/PositionService.java:33](../backend/src/main/java/org/ash/inventory/service/PositionService.java#L33) queries positions per bulk item; [backend/src/main/java/org/ash/inventory/service/EquipmentService.java:140](../backend/src/main/java/org/ash/inventory/service/EquipmentService.java#L140) queries open member damage per item, with extra commitment/loan/asset/schedule work for restricted stock. [backend/src/main/java/org/ash/inventory/resource/ApiMapper.java:74](../backend/src/main/java/org/ash/inventory/resource/ApiMapper.java#L74) finds names per requested item and history per order. [backend/src/main/java/org/ash/inventory/resource/ApiMapper.java:299](../backend/src/main/java/org/ash/inventory/resource/ApiMapper.java#L299) calls EventMetricsService, whose [backend/src/main/java/org/ash/inventory/service/EventMetricsService.java:16](../backend/src/main/java/org/ash/inventory/service/EventMetricsService.java#L16) performs three dataset reads and per-item finds per event.

Trigger: ordinary catalog page, general-order list including full history, event precache/list, or report event rebuild. Explicit work scales with items/orders/events; lazy actor/location/association expansion may add queries, but the exact number requires SQL tracing and is not presumed from annotations alone. A transactional DTO boundary avoids late REST serialization; it does not make mapping query-free.

Change: put batch loading/aggregation in ApiQueryService and focused ORM readers, then pass materialized projections to pure mappers. Reuse the corrected snapshot-policy interface for read batches, not its detached JPA reconstruction wholesale. Separate general-order summary from detail/history as faction orders already do. Keep stock authoritative and uncached across requests.

**Effort L; regression risk medium/high.** Trace SQL counts on multiple page sizes, restricted/serialized/lot items and large histories; compare quantities, visibility and DTO contents before/after. No domain lock/command refactor is needed to fix read projection loading.

### P03 — Every report page/export repeats full snapshot filtering and 27 watermarks

**P2/medium · high confidence · F17, C03/C05; reporting performance.**

Evidence: [backend/src/main/java/org/ash/inventory/service/OperationalReportService.java:39](../backend/src/main/java/org/ash/inventory/service/OperationalReportService.java#L39) loads the stored JSON rows, filters all rows and then slices a page. [backend/src/main/java/org/ash/inventory/service/OperationalReportService.java:80](../backend/src/main/java/org/ash/inventory/service/OperationalReportService.java#L80) performs 26 table watermarks plus one outbox watermark through [backend/src/main/java/org/ash/inventory/orm/OperationalReportOrm.java:10](../backend/src/main/java/org/ash/inventory/orm/OperationalReportOrm.java#L10). [src/services/reportService.ts:7](../src/services/reportService.ts#L7) repeats this for each 200-row export page. ## 8. Operational semantics retained from prior progress documentation

These distinctions are requirements/intent to preserve during fixes. Findings above identify where source does not yet satisfy them; this section is not a claim of runtime verification.

**Stock, custody and returns.** OnHand is physical warehouse/location stock; custody is material held by a person/order; available excludes reservations, unusable lots, quarantine, damage and applicable blockers. Incoming purchase quantities are in transit, not owned/onHand/available until receipt. Owned material in a physical transfer remains owned but not onHand/available. Serialized commands and reconciliation name exact assets. Pending return submissions retain custody and contribute zero warehouse availability until acknowledgement. Missing remains outstanding until a return/consumption/authorized write-off resolves it. Repair improves condition without creating quantity. A stale pending submission can be rejected with a note without undoing later physical reconciliation.

**Order/planning behavior.** Requests can exceed stock; preparation reserves validated source stock and pickup converts it to custody atomically. Reopening/cancelling releases reservations and preserves asset location. Editing an existing order credits only its own reservation against authoritative available, never subtracts global reservations twice. General orders and faction orders share allocation/custody policies but keep their distinct reservation representation and immutable histories. Forecast is total demand: use the larger of unfulfilled forecast and active requests. Reusable demand overlaps through the documented return/readiness window; consumables accumulate. Dated purchase supply covers only timely demand. Item/event/date availability is request-local computation, not a server stock response cache.

**Ownership/commitments (F19).** Visibility, owner, keeper/contact, physical storage, custodian and consent are separate. Use one item pool per owner; all its serialized units share that owner. Mixed-owner bulk uses distinct item records. Organization stock defaults available; private/external stock needs owner/provider and restricted availability. A commitment supplies quantity/exact asset identities, event/date range, pickup instructions, agreement evidence and return instructions/due date for returnables. Dates cover the full event. One overlapping commitment per pool includes the return window. Current idle usable stock is required; future offers do not assume outstanding material returns on time. Item locks and equipment revision reject stale edits. Reservations, custody, missing and transfers block ownership/policy changes and cancellation; keeper/contact metadata can change independently. Consumable usage consumes the committed cap. Returns remain possible after commitment expiry, which does not silently cancel orders or reconcile custody. Restricted shortages suggest obtaining consent, not purchasing into someone else's owner pool.

**Contributor behavior (F20).** `/contributor` is available to signed-in accounts and is the home screen for non-management roles. Read-only cannot mutate. Warehouse assignment names a real account at an exact storage location and does not imply assignment of children. Free-text keeper, ownership and visibility are not access grants. Personal responses expose only assigned storage/custody/request evidence; faction serialized custody expands to exact asset rows. Stable member command IDs prevent duplicate requests/returns. General returns share the acknowledgement queue. Quantity is bounded by outstanding minus pending. Open contributor damage conservatively blocks the entire pool; the request itself does not invent a warehouse adjustment. Staff inspect and use return/damage/repair commands, then close with evidence. Pickup coordination never moves stock. Shared SSE strips private equipment/loan/member-request detail; account-scoped REST/audit retains it.

**Reminders (F21).** `/actions` and the header use a live in-app task list, refreshed every minute and on changes. Personal deferral is at most 30 days; restoring removes deferral, and completed work disappears from transactional state. No email or push worker exists. Overdue custody uses event end; undated direct custody stays visible without an invented deadline. Receipts include undated incoming purchases. Lot warnings use the earlier expiry/best-before within 30 days. Maintenance warnings must use the same evidence/scope as checkout. Commands need connectivity.

**Scanning/labels (F22).** Browser BarcodeDetector/rear camera support and permission are required; unsupported browsers retain manual/handheld entry. Camera requires secure context and images remain on device. Stop stream/timer on success, stop, dialog close/navigation and hidden tab, including permission requests that resolve after cleanup. Aliases accept up to 128 ASCII letters/digits plus `._:-`; replacement retires the old immutable label atomically, rather than rewriting/reassigning it. Retired codes conflict rather than falling through to SKU. Target updates lock; permanent identity differs from replaceable alias. Asset scan identifies an exact asset and its parent; location scan opens location stock/preselects transfer source. Scanning alone never posts a movement.

**Borrowing/rental (F23).** Register one provider's pool at its provider location and record an exact-asset or bulk/lot commitment. Agreement precedes transport and records kind, provider/contact/location, terms/cost evidence; dates/quantity come from commitment. Transfer workflow performs physical movement. Agreement collection/return only links a completed, discrepancy-free transfer created after agreement, containing its item and provider direction, at most once. Partial quantities/assets are bounded by remaining evidence. Only collected/unreturned supply is eligible; provider-held stock is excluded even between physical return and agreement recording. Before provider return, resolve damage/missing/reservations/custody using the conservative idle-pool rule. Extensions retain consent/reason, lengthen dates and reject overlap under item lock/revision. After collected equipment returns, cancel commitment/uncollected remainder with history preserved. Rental cost is evidence, not accounting.

**Offline/recovery/reports.** Shell uses service worker; shared Cache API never stores `/api/` responses. IndexedDB catalogs, supported commands, failures/history are account-scoped. Only stock transaction, media-free damage and faction create/prepare/transition/return are queued. Assembly batch checkout, general orders, contributor commands, media, purchasing, transfers/counts, ownership/loans, labels, maintenance, reminders and report rebuild need connectivity. A queue confirmation means durable local save, not stock acceptance. Server validates actor/payload/type and applies each command with its audit in one transaction. Conflict/rejection evidence is terminal; a correction has fresh ID, reason and failed-command link, with only one applied correction chain. Unowned legacy queue commands are not replayed; no migration/export adapter is retained. Snapshots are manual, disposable, query-only and visibly stale; export pins generation. Outbox leases/retries/dead letters and append-only evidence remain active recovery behavior.

Performance evidence should be gathered on named datasets with actual catalog/asset/order/history/position/report row counts, cold/warm caches and representative roles. Record p50/p95 only from measured requests; no target or expected speedup is fabricated here.

1. **Network:** request attempts, authentication delay, headers/body time, cancellation/retries, payload bytes, SSE reconnect and duplicate invalidation; Procurement initial/event-scope/background loads, catalog edit, pickup/return, receiving, inbox and CSV completion. Measure timers rather than attributing a visible wait to staleTime.
2. **SQL:** statement count/result rows/duration by endpoint, including explicit loops and actual lazy loads; catalog page with/without images, general histories, event list, procurement snapshot, contributor/inbox and report page/export/rebuild. Capture query plans on the target PostgreSQL version when authorized.
3. **Index suitability:** compare actual predicates/orders with the baseline. Existing reservation item/status, return status/user, outbox delivery/aggregate, event transaction, history, location-parent, correction-root and commitment-date indexes are useful candidates, not proven optimal. Investigate missing declared ledger item/type/time, active asset item/code, active maintenance item/asset and stable createdAt/ID page order indexes; case-folded exact code queries and `%search%` predicates need their own plan evidence. Add only justified indexes in the baseline, not migrations.
4. **Locks:** wait duration, affected row sets, transaction length and deadlocks for multi-item order preparation/pickup, counts, transfers, receiving, loan edits and hierarchy edits. Hierarchy currently locks all warehouses/locations; retain correctness until contention justifies a scoped alternative. Long DTO aggregation inside command transactions may extend lock holding; measure it.
5. **Client CPU/render/media:** React profiler for large supplier groups/operation tables/catalog selections, current DataGrid virtualization versus unbounded cards/tables, CSV planning and QR generation. Route lazy loading and handler-level PDF imports exist. Measure bundle chunks and protected media request volume across token refresh; useMediaUrl depends on token and can refetch unchanged media, but do not cache private media across accounts.

Measure before and after each stage on the same scenarios; a passed typecheck/lint or reduced source query-call count does not establish runtime correctness or an observed performance improvement.
